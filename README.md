# Walk-In Wardrobe

**Save inspiration from anywhere. We find the pieces, in your size and budget, ready to buy.**

Walk-In Wardrobe is an add-on any fashion store can put on its site. Shoppers upload screenshots of outfits they love
(Instagram reels, posts, Pinterest), pick the pieces they want, and get real, in-stock items from the store's catalog
that fit their budget, size and material preferences. They style those pieces on a 2D mannequin, refine them with a
stylist chatbot, and add the whole look to their cart. The retailer sees what shoppers are drawn to, and what they ask
for that the catalog can't supply.

It turns the shopper's own taste (from inspo they choose) into outfits they can buy. It does **not** style clothes
the shopper already owns, and it is not a generic "you might like" feed.

> **Honesty note.** The store (**Urban Thread**), its 94 products, prices, stock, personas, orders, shopper history
> and checkout are **synthetic mocks** generated by `data/generate.py`. Urban Thread is fictional; nothing here is a real
> brand or a real integration. Checkout creates a demo order and decrements mock stock; no payment is taken. The
> retailer view includes synthetic shopper history, flagged `synthetic=true` in the event log.

**Live demo (Cloud Run, live Gemini):** https://wiw-app-nhukbiswfq-uc.a.run.app  (pick a shopper in the top-right menu)

## Run it

```bash
make setup     # Python 3.12 venv + npm install
make seed      # generate catalog, SVG images, demo inspo; load local SQLite + media folder
make dev       # API on :8000, app on http://localhost:5173  (GEMINI_MODE=replay: no network needed)
make test      # 59 backend tests + frontend type check
```

`make dev` runs the whole demo offline. Every Gemini call goes through `wiw/gemini.py`:

| `GEMINI_MODE` | Behaviour |
|---|---|
| `replay` (default) | Answer from `cache/gemini/` (recorded from real Gemini). On a cache miss, use the deterministic fallback. Never touches the network. |
| `live` | Gemini on Vertex AI (`gemini-3.8-flash`, location `global`). Responses are schema-validated and written to the cache. Any error uses the fallback. |
| `off` | Deterministic fallbacks only (used by the tests). |

To run live locally: `GEMINI_MODE=live make dev`. Credentials come from ADC, or from the gcloud CLI user token if ADC
is missing or stale (`wiw/gcp_auth.py`). To re-record the replay cache: `make demo-record`.

Other checks: `make smoke URL=...` (API smoke test) and `.venv/bin/python scripts/ui_smoke.py <url> [out] [--desktop]`
(headless browser run of the main flow, with screenshots).

## Demo script (about 3 minutes)

Run offline with `make seed && make dev`, open http://localhost:5173 on a laptop (the chat panel is always visible on
desktop), and use exactly these inputs so replay answers come from the recorded cache. Other inputs still work; they
use the deterministic planner instead.

1. You're **Aanya** (persona menu, top right). Open **Preferences**: budgets per category, size M / 28 / 5, loves linen
   and cotton, avoids polyester.
2. **Wardrobes → Add folder** with name `Old-money summer` and description `Linen, loafers and long lunches`. **Upload inspo**:
   `demo/inspo/generated/old_money_summer.png` (drag-drop, file picker, or paste).
3. Five pieces are detected, with boxes. Tap **Linen shirt, Chinos, Loafers** (3 of 5) and press **Hang 3 pieces**.
4. The hangers show "This store covers 3 of 3 pieces". Open the shirt hanger: **For you** shows the Ivory linen relaxed
   shirt; **Also view** shows reason chips: "Your size M is sold out", "₹799 over budget", "Polyester".
5. Upload `resort_linen.png` into the same folder and **Like all**. The coverage line for that look reads
   **"covers 3 of 4"**; the wide-leg linen trousers get an honest "doesn't stock a close match… closest from this store".
6. In the stylist panel: **"Make it work for a beach wedding under ₹5,000"**. The outfit card shows real items and a
   total from the database, within budget (sandals beat loafers).
7. **Try on** opens the walk-in wardrobe with the look on the mannequin. Drag a hanger from the tray onto the body, then
   **Style it for me** and try **More casual**.
8. **Demo panel** lists the pieces Aanya's alerts are watching. Press **Drop price ~22%** on one of them; the bell shows
   the notification ("…dropped from ₹X to ₹Y"). **Restock M** on the Ecru linen boyfriend shirt works the same way.
9. Back in the wardrobe, **Add full look to cart** (your sizes are auto-selected). Then **Cart → Place order (demo)**.
10. **Retailer**: the funnel, and the unmet-demand gap: wide-leg trousers saved 143 times, 0 matches in stock, plus a
    merchandiser memo written from those numbers.

Reset between rehearsals: **Demo panel → Reset demo data** (or `make seed`). For the Cloud Run deployment, reset with
`make load-cloud`: re-seeding Cloud SQL takes several minutes, which is longer than a web request allows.

## Architecture

```
 Browser (React + Vite, mobile-first)
   │  /api/*  /media/*                      one Cloud Run service (FastAPI serves API + built app)
   ▼
 FastAPI ── wiw/gemini.py ── Gemini on Vertex AI    vision (outfit split, box_2d), structured JSON,
   │          cache + fallback                       function calling (stylist), one-line copy
   ├── wiw/matching.py   deterministic scorer, tiers, coverage, complete-the-look  ◄── config/matching.yaml
   ├── wiw/catalog_search.py ── Vertex AI Search (wiw-catalog / wiw-search)  → local retrieval fallback
   ├── SQLAlchemy ── Cloud SQL for PostgreSQL (db `wiw` on the reused instance)  | SQLite locally
   ├── wiw/storage.py ── Cloud Storage (product SVGs, inspo, crops)               | local folder
   └── wiw/events.py ── BigQuery `wiw.events` + 4 views (retailer view)          | local events table
```

| Google Cloud service | What it does here |
|---|---|
| **Gemini on Vertex AI** | Splits an outfit into pieces with attributes and boxes (vocabulary-constrained JSON schema). Runs the stylist through function calling. Turns "describe yourself" into mannequin parameters. Writes one-line look reasons, the taste sentence and the merchandiser memo. |
| **Vertex AI Search** | Structured data store `wiw-catalog` and search app `wiw-search`. Retrieves candidates per piece, filtered by category and gender fit. Behind a `CatalogSearch` interface with an in-memory fallback. |
| **Cloud SQL (PostgreSQL 16)** | Operational data: users, preferences, folders, hangers, cart, orders, notifications, chat. Uses a new database on the existing `atelieros-pg` instance, not a second instance. |
| **BigQuery** | Mirror of the behaviour events, plus the views `gap_report`, `top_saved_attributes`, `coverage_summary` and `inspo_to_cart_funnel`. |
| **Cloud Storage** | Private bucket for product images, uploaded screenshots and crops, served through `/media`. |
| **Cloud Run** | One service, min instances 0, least-privilege service account `wiw-run`, DB password from Secret Manager. |

Looker was skipped: the retailer view is built into the app. The memo is written by Gemini from the BigQuery view
results; BigQuery AI functions were not needed.

### Rules the code enforces

- **Gemini handles vision and language only.** Every filter, rank, price, stock number, coverage count and cart total
  comes from deterministic code (`matching.py`, `styling.py`, `commerce.py`). Model output is validated against
  pydantic schemas whose enums are the catalog vocabulary (`wiw/vocab.py`). Products are referenced by ID and resolved
  from the database. The stylist's tools return only real rows. IDs are stripped from its text, and it is told never to
  add up prices (outfit totals come from `suggest_outfit`).
- **Every Gemini call has a cache and a deterministic fallback.** Detection falls back to ground truth for the generated
  demo images, or to an honest empty result plus tap-to-add for anything else. The stylist falls back to an intent
  planner, and copy falls back to templates. Replay never touches the network.
- **Thresholds live in config**, not code. See `config/matching.yaml` for weights, the good-match threshold, related
  subcategories, fabric and silhouette groups, tier sizes, alert thresholds, taste windows and stylist occasions.

### Matching engine (`wiw/matching.py`)

- **Style score (0–100):** a weighted overlap of subcategory, colour, pattern, silhouette, fabric, style tags (Jaccard)
  and occasion tags. Colour uses **CIEDE2000 distance in CIELAB**, not string equality. Attributes that don't apply
  (such as the sleeve of a shoe) are skipped and the remaining weights are rescaled.
- **Good match:** score ≥ 60, subcategory similarity ≥ 0.75 (a skirt never "covers" trousers), and in stock in at least
  one size.
- **Preferences are soft:** each item is checked for budget, the shopper's size being in stock, avoided materials and
  avoided colours. **For you** holds good matches that pass everything. **Also view** holds good matches that fail
  something, with reason chips; they are never hidden. Items sort by tier, then score.
- **Look coverage:** the pieces with a good match, divided by the pieces selected from that inspo, plus a second count
  for pieces covered within preferences.
- **Complete the look:** colour harmony, shared style and occasion tags, no duplicated slot, and compatibility with past
  purchases.

### Agentic extras

Price-drop, restock and new-arrival watchers (`wiw/agents.py`) run from the **Demo panel**. Each re-checks hangers
against the event with the matcher and writes notifications and `alert_sent` events. New arrivals notify only shoppers
whose taste score clears the configured threshold. **Complete the look** appears under "Style it for me". **My taste**
shows deterministic core and exploring counts, with a one-sentence summary from Gemini.

## Mock marketplace

`data/generate.py` builds one storefront deterministically:
- **Urban Thread:** 94 items across tops, bottoms, one-pieces, outerwear, footwear and accessories, with Indian price
  bands, size-level stock and price history.
- **Gaps on purpose:** no wide-leg trousers, lehengas, stilettos, kolhapuris, shrugs or leggings, and one pair of
  juttis.
- **Edge cases on purpose:** polyester look-alikes, over-budget items, "size M sold out while L is in stock", one fully
  sold-out item (for the restock alert), and one scheduled price drop.
- **Personas:** five demo shoppers with preferences, avatars, folders and past orders, plus a guest flow.

Product images are parametric **SVG flat-lays** (`wiw/garments.py`) on fixed canvases, so they sit on the mannequin
without per-item tuning. `scripts/make_images.py --photos` is reserved for a later upgrade to generated photos; nothing
depends on it. Demo inspo images are illustrated outfits drawn from the same library (`scripts/make_inspo.py`); none
are downloaded from any site. Put your own screenshots in `demo/inspo/`.

## Privacy and safety

- We never scrape Instagram, Pinterest or any retailer; shoppers upload their own screenshots.
- The vision prompt asks Gemini to describe clothing only. It must never identify or describe people, and when several
  people appear it focuses on the most prominent outfit.
- Body type, height, skin tone and hair are optional and only draw a faceless mannequin. They never affect prices or
  matches.
- There is no login beyond demo personas, and no secrets in the repo (`.env.example` only). The DB password lives in
  Secret Manager.

## Decisions made without asking

- **Project:** reused `atelieros-cup26`, which is billed and holds the earlier `atelieros*` resources. The current
  gcloud project (`rp-clean-…`, a Range Planner project) was left untouched, and your gcloud config was not changed.
- **Region:** `us-central1` rather than `asia-south1`, to sit next to the reused Cloud SQL instance. Gemini runs in
  `global`, the only location serving `gemini-3.8-flash` (verified by a live probe).
- **Model:** `gemini-3.8-flash`, the newest Flash model reachable from the project, set in `config/cloud.yaml`.
- **Gemini schemas:** Vertex rejects some JSON-schema bounds, so the schema sent to Gemini drops them. Pydantic still
  enforces them on the response.
- **Stylist trace:** the stylist sees hangers as "hanger 1..n" rather than DB IDs, so replay cache keys are stable
  across databases.
- **Cloud Run access:** the service allows unauthenticated access so the demo URL can be opened by judges. Remove it with
  `gcloud run services remove-iam-policy-binding wiw-app --member=allUsers --role=roles/run.invoker --region us-central1`.
- **Vertex AI Search retrieval:** results are topped up from local retrieval when fewer than 8 come back, because
  ranking is always done by the deterministic scorer.
- **Cloud Run credentials:** they carry no quota-project header, so the runtime account needs no
  `serviceusage.services.use`. Only local user credentials get one.
- **Jewellery slot:** earrings get their own `ears` slot, so a festive look can wear both a dupatta and jhumkas.
- **Commits:** phases 4 and 5 were committed together. They share the outfit engine, and a split commit would not have
  compiled.

## Limitations and next steps

- Live vision is not perfectly deterministic. The detection prompt defines "wide-leg" versus chinos, and
  `scripts/detect_stability.py` measured 5 of 5 identical classifications per demo image, but other screenshots can
  still be read differently from run to run. Replay mode is exact; live mode caches the first answer per image.

- Single store, single brand. `store_id` is in the schema so more can be added.
- The inventory index in Vertex AI Search isn't updated on every sale; stock is always re-checked from the database.
- The retailer memo recomputes as numbers change, so in replay it shows the template memo after live demo actions.
- Crops of real screenshots are rectangular. A segmentation mask would give cleaner hanger images.
