# Walk-In Wardrobe

**Save inspiration from anywhere. We find the pieces, in your size and budget, ready to buy.**

Walk-In Wardrobe is an add-on any fashion store can put on its site. Shoppers upload screenshots of outfits they love
(Instagram reels, posts, Pinterest) and tap the pieces they like. For each one they immediately see what the store
actually has, in their size and budget, and hang the real store piece they want. They arrange those pieces on a plain
style board (layering a jacket over a top, for example), refine them with a stylist chatbot, and add the whole look to
their cart. They can also browse the full store in **Shop**. Separately, the brand sees what shoppers are drawn to and
what they ask for that the catalog can't supply.

It turns the shopper's own taste (from inspo they choose) into outfits they can buy. It does **not** style clothes
the shopper already owns, and it is not a generic "you might like" feed.

> **Honesty note.** The store (**Urban Thread**), its 349 products, prices and stock are **synthetic mocks** generated by
> `data/generate.py` (94) and `scripts/expand_catalog.py` (255 women's high-street pieces). Urban Thread is fictional; nothing here is a real brand or a real integration. Checkout creates a
> demo order and decrements mock stock; no payment is taken. Product images are generated flat-lays until the store
> owner adds real photos (see [Product photos](#product-photos)).

**Live app (Cloud Run, live Gemini):** https://wiw-app-nhukbiswfq-uc.a.run.app. It starts empty: a new visitor sets up
their own profile.

## Run it

```bash
make setup     # Python 3.12 venv + npm install
make reset     # start fresh: delete all shopper data, load the catalog (+ your product photos)
make dev       # API on :8000, app on http://localhost:5173  (GEMINI_MODE=replay: no network needed)
make test      # backend tests + frontend type check
```

`make dev` runs offline. Every Gemini call goes through `wiw/gemini.py`:

| `GEMINI_MODE` | Behaviour |
|---|---|
| `replay` (default) | Answer from `cache/gemini/` (recorded from real Gemini). On a cache miss, use the deterministic fallback. Never touches the network. |
| `live` | Gemini on Vertex AI (`gemini-3.8-flash`, location `global`). Responses are schema-validated and written to the cache. Any error uses the fallback. |
| `off` | Deterministic fallbacks only (used by the tests). |

To run live locally: `GEMINI_MODE=live make dev`. Credentials come from ADC, or from the gcloud CLI user token if ADC
is missing or stale (`wiw/gcp_auth.py`). To re-record the replay cache: `make demo-record`.

Other checks: `make smoke URL=...` (API smoke test; it creates a throwaway shopper and deletes it again) and
`.venv/bin/python scripts/ui_smoke.py <url> [out] [--desktop]` (a headless browser runs the whole shopper journey and
takes screenshots).

## The shopper journey

1. **Welcome.** A first-time visitor sets up a profile in five short steps: name and city, which section they shop
   (women's, men's or everything), sizes and fit, budget per piece, fabrics they love or avoid, and colours and
   occasions. Everything can be edited later in **Preferences**. There are no demo personas and no passwords; the
   browser remembers the profile. The profile menu offers **Start over as someone new** and **Delete my profile & data**.
2. **Upload from the landing page** (drag-drop, file picker or paste), or inside a folder. Pieces from one screenshot
   can go into different folders: pick a folder in the "Hang pieces in" menu, or create one right there with "+ New
   folder…". An upload is filed with its first hung piece; until then it waits under "Not in a folder yet" on the home
   page. Folders have any name and description ("Goa trip", "Sangeet night"…).
3. **Tap a piece you love.** Gemini finds every piece and draws a box around each. Tapping a box (or its chip) shows at
   once what Urban Thread has for it:
   - **For you:** matches that fit your preferences.
   - **Also view:** close matches that miss one, with reason chips such as "Your size M is sold out",
     "₹799 over budget" or "Polyester".
   - **Closest from this store:** shown when there's no real match.

   **Hang this** puts that **store product** on the hanger. **Save as a wish** keeps a piece the store can't match, and
   those wishes feed the brand's unmet-demand report. **Done** records the pieces you skipped as mild "not for me"
   signals.
4. **Hangers** show the actual store piece, with your inspo crop as a small reminder. Tap one to swap in another option.
5. **Style board.** A plain white canvas. Drag hangers on (or tap **Add**), move pieces, and resize them with the corner
   handle or the toolbar. When one piece lands on another, the board asks **"Inside or outside?"** and layers them so
   both stay visible, e.g. a blazer outside a shirt, or a tee inside it. Change it any time with **Outside ↑ /
   Inside ↓**. Arrow keys move the selected piece, +/- resize it and Delete removes it. There's also undo, clear and
   save look.
   - **Style it for me** proposes combinations and lays them out on the board, with more casual, formal or festive
     options.
   - **Complete the look** suggests missing pieces that go with your past purchases.
   - **Add full look to cart** auto-selects your sizes and asks when one is sold out.
6. **Stylist chat** (side panel): "Make it work for a beach wedding under ₹5,000", "Make it more casual", "Put it on
   my board", "Add the look to my cart". Preference changes are only saved after you confirm.
7. **Shop** is the storefront, like a Zara, H&M or Myntra category page. It has Women's and Men's sections, category
   navigation with counts, subcategory chips, search, and sorting by recommended, new, price or discount. Badges show
   New, % off, Few left and Sold out. The product page has a size picker, a delivery estimate and add to cart.
8. **Cart → Place order (demo)**, **My taste** (the attributes you keep saving versus what you're exploring), and
   **Notifications** for price drops, restocks and new arrivals that match what you've hung.

## Brand admin (not linked from the shopper app)

Open **`/admin`** for the brand team's tools. **Insights** holds the funnel, unmet-demand gaps (wishes and saves the
catalog couldn't match), most-saved attributes, and a merchandiser memo written from those numbers. **Store events**
lets you drop a price, restock a size, or launch a new arrival, then watch the right shoppers get notified. It also
has "Delete all shopper data".

These endpoints require an admin token on Cloud Run (Secret Manager `wiw-admin-token`); locally they're open. Read the
token with:

```bash
gcloud secrets versions access latest --secret wiw-admin-token --project atelieros-cup26
```

## Product photos

Only the store owner adds these. They go in through the backend, never through the customer app.

```bash
make product-manifest          # writes data/product_images/manifest.csv: file name -> product (all 94)
# put your photos in data/product_images/ named by product ID: ut-001.jpg, ut-045.png, ... (jpg/png/webp)
make product-images            # publish them locally (and use them everywhere in the app)
make product-images-cloud      # publish them to Cloud Storage + Cloud SQL for the live app
```

Photos are EXIF-rotated, stripped of metadata and capped at 1400 px. Transparent PNGs are kept transparent, which looks
best on the style board. Plain white backgrounds also work well. Products without a photo keep their generated
flat-lay. `make reset` and `make load-cloud` re-apply whatever photos are in the folder.

## Starting fresh

- `make reset`: locally, deletes every profile, folder, inspo upload, hanger, cart, order, chat and event, then
  reloads the catalog and your photos.
- `make load-cloud`: does the same for Cloud SQL, Cloud Storage (deletes shopper uploads), BigQuery (recreates an empty
  events table) and Vertex AI Search. It takes about 10 minutes from a laptop (rows are inserted over the network).

The demo personas and synthetic shopper history still exist, but only as test fixtures
(`seed_all(personas=True, with_history=True)`); the app never loads them.

## Architecture

```
 Browser (React + Vite, mobile-first)
   │  /api/*  /media/*                      one Cloud Run service (FastAPI serves API + built app)
   ▼
 FastAPI ── wiw/gemini.py ── Gemini on Vertex AI    vision (outfit split, box_2d), structured JSON,
   │          cache + fallback                       function calling (stylist), one-line copy
   ├── wiw/matching.py   deterministic scorer, tiers, coverage, complete-the-look  ◄── config/matching.yaml
   ├── wiw/catalog_search.py ── Vertex AI Search (wiw-catalog / wiw-search)  → local retrieval fallback
   ├── SQLAlchemy ── Cloud SQL for PostgreSQL (db `wiw` on the reused instance)  | SQLite locally
   ├── wiw/storage.py ── Cloud Storage (product SVGs, inspo, crops)               | local folder
   └── wiw/events.py ── BigQuery `wiw.events` + 4 views (retailer view)          | local events table
```

| Google Cloud service | What it does here |
|---|---|
| **Gemini on Vertex AI** | Splits an outfit into pieces with attributes and boxes (vocabulary-constrained JSON schema). Runs the stylist through function calling. Writes one-line look reasons, the taste sentence and the merchandiser memo. |
| **Vertex AI Search** | Structured data store `wiw-catalog` and search app `wiw-search`. Retrieves candidates per piece, filtered by category and gender fit. Behind a `CatalogSearch` interface with an in-memory fallback. |
| **Cloud SQL (PostgreSQL 16)** | Operational data: profiles, preferences, folders, hangers, looks, cart, orders, notifications, chat. Uses a new database on the existing `atelieros-pg` instance, not a second instance. |
| **BigQuery** | Mirror of the behaviour events, plus the views `gap_report`, `top_saved_attributes`, `coverage_summary` and `inspo_to_cart_funnel`. |
| **Cloud Storage** | Private bucket for product images, uploaded screenshots and crops, served through `/media`. |
| **Cloud Run** | One service, min instances 0, least-privilege service account `wiw-run`, DB password from Secret Manager. |

Looker was skipped: the brand insights are built into `/admin`. The memo is written by Gemini from the BigQuery view
results; BigQuery AI functions were not needed.

### Rules the code enforces

- **Gemini handles vision and language only.** Every filter, rank, price, stock number, coverage count and cart total
  comes from deterministic code (`matching.py`, `styling.py`, `commerce.py`). Model output is validated against
  pydantic schemas whose enums are the catalog vocabulary (`wiw/vocab.py`). Products are referenced by ID and resolved
  from the database. The stylist's tools return only real rows. IDs are stripped from its text, and it is told never to
  add up prices (outfit totals come from `suggest_outfit`).
- **Every Gemini call has a cache and a deterministic fallback.** Detection falls back to ground truth for the generated
  demo images, or to an honest empty result plus tap-to-add for anything else. The stylist falls back to an intent
  planner, and copy falls back to templates. Replay never touches the network.
- **Thresholds live in config**, not code. See `config/matching.yaml` for weights, the good-match threshold, related
  subcategories, fabric and silhouette groups, tier sizes, alert thresholds, taste windows and stylist occasions.

### Matching engine (`wiw/matching.py`)

- **Style score (0–100):** a weighted overlap of subcategory, colour, pattern, silhouette, fabric, style tags (Jaccard)
  and occasion tags. Colour uses **CIEDE2000 distance in CIELAB**, not string equality. Attributes that don't apply
  (such as the sleeve of a shoe) are skipped and the remaining weights are rescaled.
- **Good match:** score ≥ 60, subcategory similarity ≥ 0.75 (a skirt never "covers" trousers), and in stock in at least
  one size.
- **Preferences are soft:** each item is checked for budget, the shopper's size being in stock, avoided materials and
  avoided colours. **For you** holds good matches that pass everything. **Also view** holds good matches that fail
  something, with reason chips; they are never hidden. Items sort by tier, then score.
- **Look coverage:** the pieces with a good match, divided by the pieces selected from that inspo, plus a second count
  for pieces covered within preferences.
- **Complete the look:** colour harmony, shared style and occasion tags, no duplicated slot, and compatibility with past
  purchases.

### Agentic extras

Price-drop, restock and new-arrival watchers (`wiw/agents.py`) run from **/admin → Store events**. Each re-checks hangers
against the event with the matcher and writes notifications and `alert_sent` events. New arrivals notify only shoppers
whose taste score clears the configured threshold. **Complete the look** appears under "Style it for me". **My taste**
shows deterministic core and exploring counts, with a one-sentence summary from Gemini.

## The rail (home page)

The home page starts from what a shopper already has with the store, not from an upload:
- **Your rail**: one generic hanger with everything bought online (orders) or in store (receipts linked through the
  Urban Thread membership), in the bag, or wishlisted (heart in the Shop or on any product). Filter by source.
- **Hang a piece in many folders**: "Add to folders" ticks any number of folders at once (or creates one). In a folder,
  "Add from your rail" does the same from the other side. Rail pieces behave like any hanger (matches, board, stylist).
- **Style on canvas** (`/board`): the white style board over the whole rail. Pieces you own are free, so the look's
  price is only what you'd still buy, and "Add to cart" skips what you own.
- **Ask the stylist**: with no folder open, the stylist styles the rail, says which pieces are already yours, and never
  re-adds owned pieces to the cart.
- **Membership is a demo**: real stores look purchases up by member number. Here "Link membership" (also offered at
  the end of onboarding) adds a small, plausible history picked from the catalog in the shopper's section, sizes and
  budgets, and is labelled as a demo in the UI. It never changes stock.
- Uploading an inspo screenshot is still there, lower on the page, as an optional way to find new pieces.

## Mock marketplace

`data/generate.py` builds one storefront deterministically:
- **Urban Thread:** 94 items across tops, bottoms, one-pieces, outerwear, footwear and accessories, with Indian price
  bands, size-level stock and price history.
- **Gaps on purpose:** no wide-leg trousers, lehengas, stilettos, kolhapuris, shrugs or leggings, and one pair of
  juttis.
- **Edge cases on purpose:** polyester look-alikes, over-budget items, "size M sold out while L is in stock", one fully
  sold-out item (for the restock alert), and one scheduled price drop.
- **Expansion (ut-201 to ut-455):** 255 women's basics in a Uniqlo / H&M / Zara-like high-street style (shirts, knits,
  wide-leg trousers and jeans, slip and shirt dresses, trench and wool coats, blazers, flats, loafers, boots, bags,
  belts, jewellery). `scripts/expand_catalog.py` downloads web product photos (never from those brands' own sites),
  Gemini describes each one in the catalog vocabulary and rejects logos, collages and men's items, model shots are
  cropped below the chin so no face is shown, and a person reviews contact sheets before `build`. Prices, sizes and
  stock are assigned deterministically. Written to `data/catalog_extra.json`; `make product-images` adds any missing
  products without touching shoppers' data. The expansion fills the wide-leg gap above, so the tests pin the base
  94-product catalog (`CATALOG_EXTRA=0`).
- **Personas:** five demo shoppers with preferences, avatars, folders and past orders, plus a guest flow.

Until real photos are added, product images are parametric **SVG flat-lays** (`wiw/garments.py`) on fixed canvases
without per-item tuning. `scripts/make_images.py --photos` is reserved for a later upgrade to generated photos; nothing
depends on it. Demo inspo images are illustrated outfits drawn from the same library (`scripts/make_inspo.py`); none
are downloaded from any site. Put your own screenshots in `demo/inspo/`.

## Privacy and safety

- We never scrape Instagram, Pinterest or any retailer; shoppers upload their own screenshots.
- The vision prompt asks Gemini to describe clothing only. It must never identify or describe people, and when several
  people appear it focuses on the most prominent outfit.
- There is no mannequin or body data: the style board is a plain canvas, so no body type or skin tone is ever asked for.
- There are no passwords; a profile id lives in the browser, and **Delete my profile & data** removes everything. No
  secrets are in the repo (`.env.example` only). The DB password and admin token live in Secret Manager.

## Decisions made without asking

- **Starting from scratch** deleted every profile, folder, upload, cart, order, event, the demo personas and the
  synthetic shopper history, locally and in the cloud. The 94-product catalog stayed so real photos can be added to it (and was later expanded to 349).
- **Brand tools** (insights, store events, data reset) moved to an unlinked `/admin` page behind an admin token. The
  shopper-facing "Retailer" tab became **Shop**, a storefront.
- **Product photos** are added from the backend (`data/product_images/` + `make product-images`), never from the
  customer app.
- **Wishes:** a piece the store can't match can still be saved as a wish, so the brand sees the unmet demand.

- **Project:** reused `atelieros-cup26`, which is billed and holds the earlier `atelieros*` resources. The current
  gcloud project (`rp-clean-…`, a Range Planner project) was left untouched, and your gcloud config was not changed.
- **Region:** `us-central1` rather than `asia-south1`, to sit next to the reused Cloud SQL instance. Gemini runs in
  `global`, the only location serving `gemini-3.8-flash` (verified by a live probe).
- **Model:** `gemini-3.8-flash`, the newest Flash model reachable from the project, set in `config/cloud.yaml`.
- **Gemini schemas:** Vertex rejects some JSON-schema bounds, so the schema sent to Gemini drops them. Pydantic still
  enforces them on the response.
- **Stylist trace:** the stylist sees hangers as "hanger 1..n" rather than DB IDs, so replay cache keys are stable
  across databases.
- **Cloud Run access:** the service allows unauthenticated access so the demo URL can be opened by judges. Remove it with
  `gcloud run services remove-iam-policy-binding wiw-app --member=allUsers --role=roles/run.invoker --region us-central1`.
- **Vertex AI Search retrieval:** results are topped up from local retrieval when fewer than 8 come back, because
  ranking is always done by the deterministic scorer.
- **Cloud Run credentials:** they carry no quota-project header, so the runtime account needs no
  `serviceusage.services.use`. Only local user credentials get one.
- **Commits:** phases 4 and 5 were committed together. They share the outfit engine, and a split commit would not have
  compiled.

## Limitations and next steps

- **Delete my profile & data** removes everything from the app database. Copies of that shopper's events already
  streamed to the BigQuery mirror stay there until the next `make load-cloud`, because BigQuery can't delete rows that
  are still in its streaming buffer.
- Live vision is not perfectly deterministic. The detection prompt defines "wide-leg" versus chinos, and
  `scripts/detect_stability.py` measured 5 of 5 identical classifications per demo image, but other screenshots can
  still be read differently from run to run. Replay mode is exact; live mode caches the first answer per image.

- Single store, single brand. `store_id` is in the schema so more can be added.
- The inventory index in Vertex AI Search isn't updated on every sale; stock is always re-checked from the database.
- The retailer memo recomputes as numbers change, so in replay it shows the template memo after live demo actions.
- Crops of real screenshots are rectangular. A segmentation mask would give cleaner hanger images.
